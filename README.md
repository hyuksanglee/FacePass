# 🔐 FacePass SDK

<!-- 로고 이미지 자리 -->

## 프로젝트 소개

**FacePass SDK**는
"화면까지 통째로 쓰거나, 판별 로직만 떼어 쓰거나"
두 가지 통합 방식을 제공하는 **Android 얼굴 인증 SDK**입니다.

액션 기반 라이브니스로 실제 사람 여부를 판별하고, 최적 품질의 얼굴 이미지를 반환하는 것까지가 SDK의 역할이며,
이후 서버 대조 및 인증은 SDK를 사용하는 앱이 담당합니다.

- **인원** : Android 1명
- **진행 기간** : <!-- 기간 입력 -->
- **minSdk** : 24
- **개발 환경** : Kotlin, Jetpack Compose

## 1) **두 가지 통합 방식 (Product Flavor 이원화)**

동일한 SDK를 사용처의 상황에 맞게 두 형태로 제공합니다.

- **Full** : 인증 화면(Compose UI)까지 포함. `FaceAuthActivity`를 실행하면 카메라 · 안내 문구 · 진행 표시 · 실패 재시도까지 SDK가 처리
- **Logic** : UI 없이 판별 로직만 제공. `FaceAuthAnalyzer`를 앱의 기존 `ImageAnalysis`에 연결하면 자체 카메라 화면에 얼굴 인증을 붙일 수 있음

```kotlin
// Logic 통합 — 기존 카메라에 Analyzer만 연결
val analyzer = FaceAuthAnalyzer(context, callback = myCallback)
imageAnalysis.setAnalyzer(executor, analyzer)
```

UI 코드는 `src/full` 소스셋에만 존재하므로, Logic 빌드에는 Compose 관련 코드가 포함되지 않습니다.

→ **`sdkType` flavor 차원(full / logic)** 으로 소스셋을 분리하고, 사용하는 모듈이 `missingDimensionStrategy`로 통합 방식을 선택하도록 설계

---

## 2) **액션 기반 라이브니스 판별**

사진·영상 재생 등의 위조를 막기 위해, 사용자에게 **고개 돌리기 동작**을 요구하고 그 수행 여부를 판별합니다.

- ML Kit이 제공하는 얼굴 각도(`headEulerAngleY`)를 상태 머신에 입력
- `NEUTRAL → ROTATING → RETURNED` 3단계 전이로 액션 완료를 판정
- 경계값 근처의 미세한 각도 변화로 상태가 진동하지 않도록 **히스테리시스** 적용

→ 프레임워크 의존이 없는 **순수 Kotlin 상태 머신**으로 분리하여 단위 테스트가 가능한 구조

---

## 3) **마스크 착용 사전 검사 (TFLite)**

라이브니스 액션을 시작하기 **전에** 마스크 착용 여부를 검사합니다.

- TFLite 마스크 감지 모델(AIZOOTech, MIT License)을 사용
- ML Kit이 crop한 얼굴 영역을 260×260으로 전처리하여 추론
- 마스크가 감지되면 `PassError.MaskDetected`(E201)를 발생시켜 사용자에게 즉시 안내

→ 인증을 끝까지 진행한 뒤 서버에서 실패하는 대신, **가장 이른 시점에 차단**하여 불필요한 재시도를 방지

---

## 4) **품질 기반 최적 프레임 선택**

인증 과정의 여러 시점에서 얼굴 후보를 수집하고, 그중 품질 점수가 가장 높은 프레임을 반환합니다.

- 수집 시점 : ① 얼굴 최초 검출 ② 액션 직전(정면 정렬) ③ 액션 완료
- 품질 점수 : 정면도(yaw · pitch · roll)와 눈 뜸 정도를 가중 합산하여 0~1로 산출
- 선택되지 않은 후보 비트맵은 즉시 `recycle()`하여 메모리 정리

```kotlin
// 정면도 35% / 상하 25% / 기울기 15% / 눈 뜸 25%
yawScore * 0.35f + pitchScore * 0.25f + rollScore * 0.15f + eyeScore * 0.25f
```

---

## 5) **에러 코드 체계**

호출 측이 로깅과 분기에 활용할 수 있도록 모든 실패를 코드 체계로 통일했습니다.

| 구분 | 코드 | 내용 | 재시도 |
|------|------|------|--------|
| 환경 | E101 | 카메라 권한 거부 | ✗ |
| 환경 | E102 | 모델 로드 실패 | ✗ |
| 환경 | E103 | 모델 준비 중 | ✓ |
| 검출 | E201 | 마스크 감지 | ✓ |
| 검출 | E202 | 다중 얼굴 감지 | ✓ |
| 판별 | E301 | 액션 시간 초과 | ✓ |
| — | E999 | 예상 밖 실패 | ✗ |

`retryable` 값으로 "다시 시도하면 될 수 있는 실패"와 "재시도가 무의미한 실패"를 구분하여, 앱이 적절한 UX를 선택할 수 있도록 했습니다.

→ SDK는 **에러 코드만 반환**하고, 사용자에게 보여줄 문구는 UI 계층(`ErrorMessage`)에서 매핑

---

## 6) **인증 결과 반환**

- 성공 : 최적 얼굴 이미지(`Bitmap`)를 앱에 전달
- 실패 : 에러 코드와 `retryable` 여부를 `Intent`로 전달
- 이미지는 크기가 크므로 `Intent` 직접 전달 대신 홀더를 통해 전달하여 `TransactionTooLargeException` 회피

# 🏗️ 아키텍처

## **모듈 구성**

```
FacePassSDK
├── face-sdk        # SDK 본체 (Android Library)
│   ├── src/main    # 로직 — Analyzer, 상태 머신, 마스크 검사, 에러 타입
│   └── src/full    # UI — 인증 화면(Compose), FaceAuthActivity
├── demo-full       # Full 통합 예제 — Activity 실행 후 결과 수신
└── demo-logic      # Logic 통합 예제 — 자체 카메라에 Analyzer 연결
```

## **패키지 구조 (face-sdk)**

```
dev.sanghyuk.face_sdk
├── api             # 공개 API — FaceAuthAnalyzer, Callback, Config, PassError
├── detection       # 검출 — ML Kit 얼굴 검출, TFLite 마스크 감지
├── liveness        # 판별 — 상태 머신, 프레임 품질 평가
├── internal        # 내부 유틸 — 얼굴 crop, 비트맵 회전, 결과 홀더
└── ui (full)       # 인증 화면 — Compose UI, 상태 표현
```

**설계 원칙**

- 프레임워크 의존이 없는 판별 로직(`liveness`)을 분리해 단위 테스트 가능하도록 구성
- UI를 별도 소스셋으로 분리해 Logic 빌드에서 완전히 제외
- SDK는 판별과 촬영까지만 책임지고, 서버 통신 및 정책은 앱에 위임

# ✅ 테스트

프레임워크에 의존하지 않는 순수 로직을 대상으로 단위 테스트를 작성했습니다.

**`LivenessStateMachineTest`**
- 정면 상태에서의 초기 상태 판정
- 충분한 회전 후 복귀 시 액션 완료 판정
- 회전 각도가 부족할 경우 통과되지 않음
- 경계값 노이즈 상황에서의 상태 안정성(히스테리시스)

**`FrameQualityTest`**
- 정면일수록 높은 점수 산출
- 완전 정면의 점수 상한 확인
- 눈 뜸 확률이 없는 경우(classification 미사용) 중립값 처리
- 각도가 임계를 초과할 때 점수 수렴

```bash
./gradlew :face-sdk:testLogicDebugUnitTest
```

# 🐞 트러블슈팅

## ML Kit만으로는 마스크 착용을 걸러낼 수 없는 문제

### 문제

인증을 정상적으로 완료했는데도, 반환된 얼굴 이미지에 **마스크를 착용한 상태가 그대로 담기는** 경우가 발생했다.

이 이미지가 서버로 전송되면 등록된 얼굴과 대조에 실패하게 되고, 사용자는 인증을 처음부터 다시 수행해야 한다.
더 큰 문제는 **사용자가 실패 원인을 알 수 없다**는 점이었다. 화면상으로는 인증이 정상적으로 진행되었기 때문이다.

### 원인

ML Kit Face Detection은 "화면에 얼굴이 존재하는가"를 판단하는 검출기다.
마스크는 얼굴의 하관을 가릴 뿐 검출 자체를 방해하지 않기 때문에, 마스크를 착용해도 얼굴은 정상적으로 검출되고 각도 정보도 그대로 제공된다.

즉 검출 단계에서는 통과할 수밖에 없고, **"이 얼굴이 인증에 사용할 수 있는 상태인가"는 별도로 판단해야 하는 문제**였다.

### 해결 과정

#### ✔ 1) 마스크 판별 모델 도입 및 검사 시점 결정

TFLite 마스크 감지 모델을 추가하고, 검사 시점을 **라이브니스 액션을 시작하기 전**으로 잡았다.

액션 완료 후에 검사하면 사용자가 고개를 돌리는 과정을 모두 수행한 뒤에 실패하게 된다.
얼굴이 검출된 직후에 검사하면, 마스크 착용자는 불필요한 동작을 수행하기 전에 안내를 받을 수 있다.

```
얼굴 검출 → [마스크 검사] → 라이브니스 액션 → 최적 프레임 선택
              ↑ 여기서 차단
```

#### ✔ 2) 통합형 모델을 파이프라인에 맞게 단순화

도입한 모델(AIZOOTech)은 SSD 구조로 **얼굴 검출과 마스크 분류를 함께 수행**하는 형태였다.
출력은 5,972개 앵커에 대한 박스 좌표(`loc_branch`)와 분류 결과(`cls_branch`)로 구성된다.

원본 방식대로 사용하려면 앵커 디코딩과 NMS(비최대 억제) 후처리를 구현해 박스 좌표를 복원해야 한다.
그러나 이 파이프라인에서는 **ML Kit이 이미 얼굴 위치를 확정**했으므로, 모델이 다시 찾아낸 박스 좌표는 사용할 곳이 없었다.

따라서 crop된 얼굴을 입력하고 **분류 결과만 확인하는 방식**으로 단순화했다.
검출 책임은 ML Kit이, 마스크 판별 책임은 TFLite 모델이 갖도록 역할을 분리한 것이다.

#### ✔ 3) 실패를 UX로 처리

마스크 감지는 사용자가 마스크를 벗으면 해결되는 실패이므로, 인증을 종료하지 않고 재시도를 유도하도록 했다.
`retryable = true`인 에러는 화면을 유지한 채 실패 상태로 전환하고, 다시 시도 버튼을 노출한다.

### 결과

마스크를 착용한 상태에서는 액션을 수행하기 전에 안내를 받게 되어, 불필요한 인증 진행과 서버 왕복이 발생하지 않는다.
또한 검출과 판별의 책임을 명확히 분리함으로써, 이후 다른 판별 기준(예: 조도, 가림 여부)을 추가할 때도 동일한 위치에 확장할 수 있는 구조가 되었다.

# 💬 회고

FacePass SDK는 기능을 구현하는 것보다 **"SDK가 어디까지 책임질 것인가"를 정하는 일**이 더 어려웠습니다.

얼굴 인증은 카메라 화면, 판별 로직, 서버 대조, 실패 처리까지 넓은 범위에 걸쳐 있습니다.
이를 모두 SDK가 떠안으면 사용하는 앱의 상황에 맞추기 어려워지고, 반대로 너무 적게 담으면 붙이는 쪽의 부담이 커집니다.

그래서 **"살아있는 사람의 얼굴 이미지를 만들어 반환하는 것까지"** 를 SDK의 책임으로 정하고,
서버 통신과 인증 정책은 앱에 위임했습니다. 동시에 UI가 필요한 경우와 그렇지 않은 경우를 모두 지원하기 위해
Product Flavor로 통합 방식을 이원화했습니다.

마스크 판별 모델을 도입할 때도 같은 기준을 적용했습니다.
모델이 제공하는 기능을 전부 사용하는 대신, 이 파이프라인에서 실제로 필요한 부분만 취해 역할이 겹치지 않도록 했습니다.

향후에는 프레임 선명도(흔들림) 평가를 추가해 최적 프레임 선택의 정확도를 높이고,
얼굴 검출이 일시적으로 끊기는 상황에 대한 허용 범위를 조정해 사용성을 개선할 예정입니다.
